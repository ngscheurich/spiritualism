## Question

What does microsandbox expose today? Capture: how sandboxes are created, listed, and stopped programmatically (CLI, SDK, or API, and in which languages); host requirements (OS, virtualization, install method); how filesystem access (mounts, shared directories) and network policy are controlled; how processes run inside a sandbox and how their I/O and exit status reach the host; current project maturity and license. Primary sources only: official docs and source.

## Context

Findings branch: `research/microsandbox` (never merged). Findings file on that branch: `docs/research/microsandbox.md`.

## Answer

- microsandbox is a local-first microVM runtime. Each sandbox is a VM with its own Linux kernel, filesystem, and network stack, booted as a child process of the caller; there is no daemon. It is built on `libkrun` (VMM) and `smoltcp` (network stack).
- Create/list/stop, CLI: `msb create <image> --name <n>` (boots immediately), `msb run`, `msb ls` / `msb ps` / `msb inspect` (all with `--format json`), `msb stop [--force]`, `msb kill`, `msb rm`, `msb pause` / `msb resume`, `msb wait`. Config file via `msb run --conf sandbox.yaml`.
- Create/list/stop, SDKs: TypeScript, Rust, Python, Go, Ruby, with a parallel lifecycle API (`create`, `list`, `get`, `stop`, `start`, `kill`, `destroy`/`remove`). Local SDK sandboxes stop when the application exits unless created detached; detached sandboxes reconnect by name; `connect_or_create` reuses a running sandbox. Defaults at create: 1 vCPU, 512 MiB, public-only networking. The cloud REST API (private beta) covers lifecycle, snapshots, volumes, and billing, but not exec, streaming, PTY, or file transfer.
- Host requirements: Linux needs KVM (`/dev/kvm` readable and writable by the user), glibc 2.28+, x64 or ARM64; musl-only hosts cannot run the local runtime. macOS is Apple Silicon only (Hypervisor.framework); Intel Macs unsupported. Windows 10+ with Windows Hypervisor Platform, labelled "preview". The per-sandbox host process runs as the launching user, no root, no setuid. Nested use (inside a VM, container, or CI runner) requires the outer environment to expose `/dev/kvm`; `--privileged` does not create a missing KVM device.
- Install: `curl -fsSL https://install.microsandbox.dev | sh`, Homebrew tap, `npm i -g microsandbox`, `uv tool install microsandbox`, `cargo install microsandbox`. SDKs need two runtime files (`msb` executable and `libkrunfw` library, default `~/.microsandbox`); `ensure_runtime` installs them, and "Sandbox creation does not download it automatically". Language floors from manifests: Python >=3.10, Node >=22, Go 1.22, Ruby 3.3+ (Ruby currently also needs a Rust toolchain because platform gems are not yet published). Python SDK is a pyo3 native extension; Node SDK is a napi-rs native addon; Go SDK calls an internal FFI library.
- Filesystem access, three mechanisms: (1) a filesystem API over the control channel (`fs().read/write/list/readStream/copyFromHost`; CLI `msb copy`), no mount and no network, recommended for small files; (2) bind mounts of host directories or single files via virtio-fs, bidirectional, with `ro`/`rw`, `noexec`, `nosuid`, `nodev`, `quota`, `uid=,gid=` options; (3) named volumes (persist under `~/.microsandbox/volumes/`), owned volumes, disk-image volumes, tmpfs. In-guest defaults are permissive (mounts writable and executable, workload runs as root); an opt-in `restricted` profile tightens this but breaks `sudo` and Docker-in-Docker.
- Network policy: all guest traffic terminates in a host-side user-space stack; every packet is checked against policy. Default allows public egress plus DNS and denies private ranges, loopback, link-local, cloud metadata, and the host; ingress only on published ports bound to `127.0.0.1`. Profiles `public`, `private`, `host` compose; `none` and `all` are whole-policy. Low-level: `default_egress`/`default_ingress` plus ordered first-match rules on groups, IPs, CIDRs, domains, port ranges. Hostname allowlists fail closed for HTTPS unless TLS interception is on. The host is reachable at `host.microsandbox.internal` only when the `host` group is allowed.
- Process execution: one host-driven control channel over `virtio-console` to `agentd` (PID 1, root, in the guest). The guest cannot initiate requests to the host over this channel. Host-side SDK/CLI connect to a per-sandbox relay socket (`agent.sock`). Wire format: `[length u32][id u32][flags u8][CBOR envelope]`, 4 MiB frame limit. Exec works with networking disabled.
- I/O and exit status: `exec(cmd, args)` returns exit code, stdout, stderr in every SDK; per-exec `cwd`, `env`, `timeout`, `rlimit`, `user`. `exec_stream` yields `Started{pid}`, `Stdout`, `Stderr`, `Exited{code}` events with a session ID; stdin can be piped and a TTY requested (`tty: true`). Interactive PTY attach: `attach_shell`, `attach_with`, CLI `msb exec -t`, `Ctrl+]` detaches. The Ruby SDK does not expose streaming, attach, or session IDs. Detached background jobs (`msb exec -d`, `msb jobs/logs/attach/wait/signal/kill`) are new in v0.7.8 and local-only. `msb logs` / SDK `logs()` read output after stop or crash.
- Maturity and license: Apache-2.0. The README says "Microsandbox is still **beta software**. Expect breaking changes, missing features, and rough edges." Current release v0.7.8 (2026-10-09); ten releases between 2026-09-09 and 2026-10-09. `COMPATIBILITY.md` places public SDK, CLI, and HTTP API compatibility outside its scope (the findings infer, not quote, that no public-API stability is promised). `SECURITY.md` names only the Python and Node SDKs as in scope. Repo is `github.com/superradcompany/microsandbox`; README says "BACKED BY Y COMBINATOR".
- Unverified in the findings: whether `msb exec` sets its own exit status to the guest command's exit code outside the Docker example; which binary (SDK process or `msb` child) hosts the VMM; GitHub star/fork/issue counts; the README's sub-100 ms boot claim. Nothing was executed; all claims come from docs and source text.
