# Research: client-server IPC options

Map: ../map.md
Type: research
Status: resolved
Blocked by:

## Question

What are the viable transports and protocols for a local client-server model where the server owns long-lived processes and PTYs, and clients attach for interactive use? Survey JSON-RPC 2.0 over Unix domain sockets, gRPC, HTTP+SSE/WebSocket on localhost, and others worth naming. For each: framing, bidirectional notifications, streaming, PTY attach, library support across likely stacks, Windows/macOS/Linux portability. Primary sources only: specs and official library docs.

## Context

Findings branch: `research/ipc-options` (never merged). Findings file on that branch: `docs/research/ipc-options.md`.

## Answer

- The findings survey trade-offs and recommend nothing. Nothing was run; every claim is from specs and official library docs. Three concerns dominate: framing on a byte stream, server-initiated push, and a raw byte channel for PTY I/O plus an out-of-band resize call.
- JSON-RPC 2.0: the spec defines no framing ("transport agnostic"). Two shipped conventions: LSP's `Content-Length` header block and MCP's newline-delimited messages. Notifications (a request without `id`) are built in and flow server-to-client in LSP (`$/progress`) and MCP. No stream primitive; progress is repeated notifications. No binary type, so PTY bytes need base64 or a side channel (the findings' inference). Libraries: Node `vscode-jsonrpc` (pipe transport picks a Unix socket or `\\.\pipe\` name behind one API); Go stdlib `net/rpc/jsonrpc` is 1.0 only; Rust `jsonrpsee` has HTTP and WS clients, no Unix-socket transport named; Python stdlib implementation not found (unverified absence).
- gRPC: HTTP/2 framing with a 5-byte length prefix per message; four call shapes including bidirectional streaming with per-stream ordering, deadlines, and cancellation. No server-initiated calls; push is a long-lived server-streaming RPC (inference). PTY attach fits as a bidi stream of `bytes`; resize as a field or a unary call. Naming: `unix:` and `unix-abstract:` are "Unix systems only"; Windows named pipes are not mentioned (grpc-go's `WithContextDialer` plus `passthrough` could enable a pipe dialer; unverified for other languages). Official libraries for Node (`@grpc/grpc-js`, pure JS, registers a `unix` resolver), Go, Python (`grpcio`), Rust (tonic; its uds example is `cfg(unix)`), and nine more. `Bun.serve` states gRPC response trailers are unsupported; `@grpc/grpc-js` under Bun unverified.
- HTTP + SSE: push only, "always decoded as UTF-8", auto-reconnect with `Last-Event-ID`. Client-to-server needs separate requests (MCP Streamable HTTP: a POST per client message, GET opens an SSE stream). Not a fit for raw PTY bytes without encoding plus a second channel (inference). Localhost HTTP servers must validate `Origin` and bind to `127.0.0.1` per MCP guidance.
- WebSocket (RFC 6455): bidirectional over one TCP connection; text and binary frames; 7/16/64-bit lengths; client-to-server masking; ping/pong; close codes. No request/response correlation in the RFC; an RPC layer rides on top. Binary frames carry PTY bytes natively; resize is an application message. Docker exposes `/containers/{id}/attach/ws`. Libraries: Node core has a client only (server needs a package); `Bun.serve` has server and client WebSockets (upgrade is HTTP/1.1 only; `unix:` plus upgrade together unverified); Go `coder/websocket` or `gorilla`; Rust `tokio-tungstenite`; Python `websockets`. WebSocket over a Unix socket or named pipe is library-dependent; only TCP is specified.
- Docker hijack pattern: `POST /containers/{id}/attach` hijacks the HTTP connection to raw bidirectional bytes; without a TTY an 8-byte multiplex header (stream type + big-endian size); with a TTY "simply the raw data from the process PTY". Resize is a separate `POST /containers/{id}/resize?h=&w=`. Multiple attach and reattach are supported. Docker-specific, not a standard; proxies need the `Upgrade: tcp` hint.
- Others: MessagePack-RPC (self-delimiting values, notifications, bin type unverified; Neovim uses it over a default socket, `--listen` pipe/TCP, or `--embed` stdio, with out-of-spec LIFO response ordering). Cap'n Proto RPC (symmetric capabilities, Rust `capnp-rpc` covers Level 1; JavaScript listed as Node.js only, no Bun/TS; streaming unverified). Connect (gRPC-compatible; bidi streaming needs HTTP/2; Rust exists only as an RFC). ttrpc (containerd; 10-byte header, 4MB max, "Server initiated streams are not currently supported"; Go-only as read). stdio transport (MCP, Neovim `--embed`) inverts ownership: the client spawns the server, which conflicts with a server that outlives clients (inference). tmux control mode: newline-delimited commands, `%begin`/`%end` blocks, `%output pane-id value` notifications with octal escaping, `refresh-client -C` for size.
- Transport portability by stack: Node `net` handles Unix sockets and Windows named pipes (`\\?\pipe\`, `\\.\pipe\`) behind one `path` API. Go `net` has no named-pipe support; Microsoft's `go-winio` adds it. tokio has `UnixStream` ("Available on Unix") and a separate `windows::named_pipe` module. Python asyncio Unix-socket APIs are "Availability: Unix"; `multiprocessing.connection` adds `AF_PIPE` but pickles payloads (Python-to-Python only). Windows 10 build 17063+ has `AF_UNIX` for `SOCK_STREAM` only with "no support for ancillary data" (no fd passing); none of the Node/Go/tokio/asyncio docs read claim their Unix-socket APIs work on Windows.
- Unix domain socket specifics: `sun_path` is 108 bytes on Linux (Node: 107 Linux, 103 macOS). Pathname sockets honor directory permissions on Linux, but "Portable programs should not rely on this feature for security." `SO_PEERCRED` gives peer credentials. `SCM_RIGHTS` can pass the PTY fd itself, the one surveyed mechanism that avoids proxying bytes. The socket file persists after a crash until unlinked (Python 3.13+ `cleanup_socket`). Linux abstract namespace sockets have no permissions. Comparable tools: tmux uses `/tmp/tmux-UID/` (directory must not be world-accessible); Docker `unix:///var/run/docker.sock` is root-only by default; Neovim says localhost TCP is "generally less secure than named pipes"; VS Code's LSP client generates random socket paths under `XDG_RUNTIME_DIR` or the temp dir.
- Windows: named pipes are `\\.\pipe\<name>`, removed when the last reference closes, and "accessible remotely" if the server service runs (deny `NT AUTHORITY\NETWORK` for local-only). Docker's Windows default is `npipe:////./pipe/docker_engine`. ConPTY exposes a PTY as two pipe handles plus `ResizePseudoConsole`, not one fd, so passing a PTY fd to a client is not portable; proxying bytes through the IPC channel is.
- Unverified (from the findings' own list): Bun compatibility of `vscode-jsonrpc`, `@grpc/grpc-js`, `ws`; `Bun.serve` `unix:` with WebSocket upgrade; Python `grpcio` Unix-socket support; gRPC over named pipes outside grpc-go; Node `Http2Server` on an IPC path; MessagePack bin type and framing; Cap'n Proto streaming and transports; Connect Unix-socket support; ttrpc outside Go; whether Neovim's "pipe" means Windows named pipes.
